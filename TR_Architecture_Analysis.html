2. CODEVASP 구조

모델: Hub Relay + 정적 레지스트리

CODEVASP는 레지스트리 역할(퍼블릭키 사전 등록/조회)과 Hub relay 역할(암호문 중개 전달)을 동시에 수행한다. VASP가 상대방 엔드포인트에 직접 통신하는 P2P 모델이 아니다.

코드 근거

// CodeVaspAdapter — protocol-adapter.ts
const url = `${this.baseUrl}/v1/code/transfer/${target.vaspEntityId}`;
// baseUrl = 'https://trapi-dev.codevasp.com'  ← CODE 서버에 POST

빗썸 엔드포인트로 직접 보내는 것이 아니라, trapi.codevasp.com에 POST하면 CODE 서버가 빗썸에 중개 전달.

데이터 흐름

송신 VASP              CODE Server                 수신 VASP
    │                 trapi.codevasp.com               │
    │                       │                          │
    │  POST /v1/code/       │                          │
    │  transfer/{vaspId}    │                          │
    │  {                    │                          │
    │    payload: NaCl(     │                          │
    │      수신키, IVMS101) │  ← 암호문                │
    │    amount, currency   │                          │
    │  }                    │                          │
    │──────────────────────►│                          │
    │                       │  CODE가 수신VASP에 relay  │
    │                       │  (암호문 그대로 전달)      │
    │                       │─────────────────────────►│
    │                       │                          │
    │                       │  ❌ payload 복호화 불가   │

실제 API 요청 본문

{
  "transferId": "uuid",
  "currency": "BTC",
  "amount": "1.0",
  "payload": "NaCl(수신VASP키, IVMS101)=kF8x9...",  ← 🔒 암호문
  "address": "bc1qxy2kgdyg...",
  "isExceedingThreshold": true
}

키 관리

  • 퍼블릭키를 사전 등록(정적 레지스트리)
  • 송신 VASP가 레지스트리에서 수신 VASP 퍼블릭키 조회 → NaCl Box 암호화
  • 수신 VASP 엔드포인트는 알 필요 없음 (CODE가 라우팅)

3. VerifyVASP 구조

모델: Hub Relay + Enclave + 동적 키 교환

VerifyVASP는 각 VASP에 Enclave Docker를 설치하고, Central Server가 Enclave 간 메시지를 중개한다. 퍼블릭키를 사전 등록하지 않고, 통신 시점에 실시간으로 키를 생성하고 교환한다.

핵심 컴포넌트

컴포넌트위치역할
EnclaveVASP 자체 인프라 (Docker)키 생성/관리, PII 암호화/복호화
Central ServerVerifyVASP 운영키 교환 브로커 + 암호문 relay
VASP BackendVASP 자체비즈니스 로직 + Enclave API 호출

키 교환 프로세스 (VV 문서 Step 10~16)

① 송신 Enclave: 캐시에 수신VASP 퍼블릭키 있는지 확인
② 없으면 → Central Server에 수신VASP 퍼블릭키 요청
③ Central → 수신VASP Enclave에 키 요청 전달
④ 수신VASP Enclave: 새 키쌍 생성
⑤ 수신VASP → Central → 송신VASP Enclave에 퍼블릭키 반환
⑥ 송신 Enclave: 캐시에 저장 (이후 재사용)

데이터 흐름 (VV 문서 Step 17~21)

VASP 백엔드         Enclave A          Central Server        Enclave B          수신 VASP
    │                   │                   │                   │                   │
    │  평문 PII 전달    │                   │                   │                   │
    │──────────────────►│                   │                   │                   │
    │               암호화(수신키)          │                   │                   │
    │                   │  암호문 전송      │                   │                   │
    │                   │──────────────────►│                   │                   │
    │                   │                   │  암호문 relay     │                   │
    │                   │                   │──────────────────►│                   │
    │                   │                   │              복호화(프라이빗키)        │
    │                   │                   │                   │  평문 PII 전달    │
    │                   │                   │                   │──────────────────►│

VV 필수 구현 API (VASP 측)

  • Verify User Account API — 계정 소유권 확인
  • Verify User API — 사용자 정보 검증
  • Check Transaction Status API — 트랜잭션 상태 확인
  • Callback API — 비동기 결과 수신
  • Database Setup — Enclave 전용 DB 구성

4. Sumsub 구조

모델: Hub Relay + 프로토콜 변환 게이트웨이

Sumsub은 VASP로부터 평문 PII를 API로 직접 전달받아, TRUST/GTR/TRP 등의 프로토콜로 변환하여 상대방 VASP에 전송한다.

실제 API 요청 본문

POST /resources/applicants/{applicantId}/kyt/txns/-/data

{
  "type": "travelRule",
  "applicant": {
    "firstName": "홍",            ← 🔓 평문
    "lastName": "길동",            ← 🔓 평문
    "dob": "1992-05-08",          ← 🔓 평문
    "address": {
      "country": "KOR",
      "town": "Seoul",
      "street": "강남대로 123"     ← 🔓 평문
    }
  },
  "info": {
    "direction": "out",
    "amount": "1.0",
    "currencyCode": "BTC"
  }
}
⚠️ PII 평문 노출
이름, 생년월일, 주소가 평문 JSON으로 Sumsub 서버에 전달된다. Sumsub이 이를 TRUST/GTR 프로토콜로 변환하는 과정에서 Sumsub 서버가 PII를 직접 처리.

CODE/TTR API와 비교

필드CODE/TTR APISumsub API
이름❌ (payload 안에 암호화)✅ firstName, lastName 평문
생년월일❌✅ dob 평문
주소❌✅ address 평문
지갑주소✅ 메타데이터✅
금액✅ 메타데이터✅

Sumsub의 장점

  • 크로스 네트워크: TRUST, GTR, TRP, Sygna 등 멀티 프로토콜 지원
  • Email fallback: 어디에도 안 속한 VASP에 이메일 기반 통보
  • SDK 제공: 개발 부담 최소

5. TranSight TR 구조

모델: Hub Relay + 정적 레지스트리 + KYT 원자적 통합

TTR은 CODEVASP와 동일한 구조(정적 레지스트리 + Hub relay + NaCl Box E2E)에 KYT 원자적 통합과 Protocol Adapter 기반 크로스 네트워크 확장을 추가한 모델.

7. 키 교환 방식 비교

CODEVASP (정적):
  "빗썸 키 뭐야?" → 레지스트리 조회 → "여기 있어" → 끝

VerifyVASP (동적):
  "빗썸 키 줘" → Central → 빗썸Enclave: "새로 만들게"
  → Central → 송신Enclave: "받았다, 캐시함"

Sumsub:
  키 교환 없음 — 평문 PII를 Sumsub에 전달, Sumsub이 알아서 처리

TTR (정적 — CODE와 동일):
  "빗썸 키 뭐야?" → vasp-registry 조회 → "여기 있어" → 끝

8. 금융기관 망분리 문제

금융기관(은행, 증권사)은 망분리 규정으로 외부 VASP 엔드포인트에 직접 HTTP 요청 불가.

✅ 해결: Hub Relay 구조
CODEVASP, VV, Sumsub, TTR 모두 이미 Hub relay 구조이므로 금융기관은 Hub 엔드포인트 1개만 화이트리스트에 등록하면 모든 VASP와 통신 가능.

9. TTR 포지셔닝

TTR = CODEVASP 동일 구조 + 3가지 확장
  1. KYT 원자적 통합 — PII 전송 전 위험 주소 자동 차단
  2. Protocol Adapter — CODE, Sumsub, VV, Direct 멀티 프로토콜 라우팅
  3. 금융기관 호환 — Hub relay로 망분리 자연 해결
